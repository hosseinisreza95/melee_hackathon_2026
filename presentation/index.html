GouvernanceLes règles que le code rend impossibles à contourner

Chaque assertion a sa preuve

source, URL officielle, date de collecte UTC, statut de validation, extrait de la ligne source : colonnes NOT NULL. Une ligne sans preuve est refusée par la base.

L'original n'est jamais écrasé

« Full Registration » reste à côté de active ; « Fraisier » à côté de Strawberry · FRAAN · to_verify. Les codes EPPO sont des candidats tant qu'un humain ne les a pas validés.

Absence ≠ absence d'homologation

trois états distincts : trouvé non trouvé dans la source (date) source non connectée. Le 404 de l'API le dit en toutes lettres.

Humain dans la boucle

chaque changement de statut passe par POST /review : relecteur, date, justification journalisés. La confiance machine n'est pas une validité réglementaire.

Honnêteté et suiteCe que ce prototype n'est pas — et ce qu'il devient

Limites connues

  • 4 sources ; Allemagne sondée mais écartée, Belgique/Uruguay/Mexique non collectés.
  • Dose CA/US uniquement via l'étiquette (IA, à vérifier) ; appariement culture/cible non affirmé par ces sources.
  • Brésil : produits actifs seulement, pas de dates.
  • Codes EPPO = candidats to_verify (~23 % des usages codés).
  • API sans authentification (données publiques) ; Entra ID documenté, pas construit.

Chemin vers la production

  • Même code sur Azure : Azure OpenAI, API Management + Entra ID, Container Apps Jobs pour la collecte.
  • Nouvelles sources = une classe de collecteur ; extraits gelés de l'organisateur comme type de source.
  • Client EPPO Data Services pour passer les codes en validated sous contrôle RA.
  • Détection de changements déjà en place : il suffit de laisser tourner le cron.
